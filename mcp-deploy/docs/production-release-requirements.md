# mcp-deploy Production Release Requirements

## Goal

mcp-deploy should let the user redeploy this project to a new production
environment with minimal manual input.

The expected flow is:

1. The user provides production-specific values.
2. The user asks AI to publish production through local MCP tools.
3. AI calls mcp-deploy tools instead of hand-written SSH, sshpass, docker, or
   compose terminal commands.
4. mcp-deploy validates configuration, builds and pushes images, initializes the
   remote deploy directory, starts services, and verifies the result.
5. The flow only stops for missing user-owned values, unresolved conflicts, or
   unrecoverable environment issues.

## Configuration Model

Use two local configuration scopes:

- `mcp-deploy/.env`: local MCP release control. This stores SSH connection data,
  SSH password or key path, Harbor login credentials, remote deploy path, and
  release-control defaults. It is never uploaded to production.
- `.env.deploy`: business runtime source configuration. This stores container
  runtime values such as database URLs and business API URLs. mcp-deploy filters
  and uploads a generated production `.env.deploy` from this source.

Harbor values are split by purpose:

- `HARBOR_USERNAME` and `HARBOR_PASSWORD` stay local in `mcp-deploy/.env`.
- `HARBOR_URL` and `HARBOR_PROJECT` may be included in the generated remote
  runtime env because production compose needs them to resolve image names.

The generated remote `.env.deploy` must include a managed marker. If the remote
file already has the marker, mcp-deploy may overwrite it automatically. If the
remote file has no marker, mcp-deploy must stop and request confirmation before
overwriting.

## Defaults and Required Values

The user should only maintain environment-specific values.

- `IMAGE_TAG` defaults to a timestamp-generated value when no env or tool
  argument overrides it.
- Non-critical release values should use MCP defaults when absent.
- Critical connection and credential values must not be empty or placeholders.
- Internal generated secrets, such as `POSTGRES_PASSWORD`, may be generated by
  MCP and written back, but the resulting database must still be validated.

Env priority is:

1. Explicit tool argument
2. Explicit env value
3. MCP-generated value
4. MCP default

## Missing Configuration Flow

mcp-deploy should not guess unknown production values such as new business API
hosts and ports.

When required configuration is missing, empty, or still a placeholder, MCP
returns a structured `needs_input` response. AI uses that response to ask the
user for all missing values in one batch, then calls an MCP completion tool to
write values back to the correct local configuration file.

The same `needs_input` mechanism applies to SSH details, Harbor credentials,
database URLs, and business API URLs.

## Runtime Key Discovery

mcp-deploy should combine a maintained runtime-key allowlist with source-code
discovery:

- The allowlist defines known required production runtime keys.
- Code scanning finds likely new runtime keys, such as `os.getenv("NEW_API")`.
- Discovered keys not present in the allowlist should be included in
  `needs_input` and marked as discovered, so AI can ask the user whether and how
  to fill them.

This avoids guessing new API addresses while still surfacing newly introduced
runtime dependencies.

## Validation Policy

Database configuration is machine-verifiable and must be a hard gate:

- Validate connection.
- Validate authentication.
- Validate the target database exists.

Business API configuration is required but not fully machine-verifiable:

- Missing, empty, malformed, or placeholder business API URLs block release.
- Configured business API URLs do not require hard HTTP validation by default.
- Optional health endpoint metadata may enable HTTP reachability checks, but
  failures should be warnings unless explicitly configured as hard requirements.

## Release and Confirmation Policy

Normal releases should not require step-by-step confirmation.

Confirmation is required only when MCP cannot safely proceed, including:

- Missing SSH or required connection details.
- Missing local `sshpass` when password SSH is selected.
- Missing remote Docker or Docker Compose.
- Remote non-managed env file overwrite.
- Container or port conflict.
- Dependency installation requirement.
- Unrecoverable validation or startup failure.

mcp-deploy should not install local or remote system dependencies automatically.
It should report missing dependencies and provide an actionable manual fix list.

## Remote Deployment Policy

mcp-deploy may automatically initialize a new production environment by:

- Creating the remote deploy directory.
- Uploading `docker-compose.prod.yml`.
- Uploading the filtered generated `.env.deploy`.
- Running compose config preflight.

mcp-deploy must not automatically stop, remove, or replace unrelated production
containers. Conflicts must stop the release and require human decision.

## Verification Policy

After compose up, MCP should verify:

- Target containers are `Up`.
- Recent logs do not show startup-level failures such as `exec format error`,
  import errors, permission errors, connection refused, or address conflicts.
- Backend health endpoint responds.
- Frontend root responds.

Business workflow validation remains a manual acceptance step unless explicit
machine-checkable health endpoints are configured.
